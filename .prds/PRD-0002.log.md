# PRD-0002 log

## T-010 -- 2026-10-24

With T-009 in, a live click on the Apple menu still returned "settled" on the menu-bar highlight
alone, and the menu turned up seconds later. A wire-level probe (a second connection, timing
every update after the click) showed where the time went:

- The click and the highlight are fast: a 2992x10 strip arrives about 80 ms after the click.
- With the menu open, the incremental stream then sends one thin, full-width band about once a
  second (rows 0-10, 6-24, 20-38, 34-60), never the menu body.
- The menu body (614x690 framebuffer px) arrives only once the menu closes: after `esc`, the
  server bursts through the backlog in about 300 ms, menu drawn and then removed.
- None of these changed it: the server's native pixel format (BGRX) instead of RGBX; ZRLE only;
  Raw only; a same-position pointer event every 100 or 250 ms; a Shift tap with the menu open.
- A non-incremental request is answered from a fresh capture: 53 ms for the 700x800 area of the
  menu, about 450 ms for the full 2992x1934 frame.

Earlier runs had also shown full-screen updates arriving two or three times a second. That was
the Mac being used at the time; an idle desktop sent one clock update in five seconds.

Options put to Aaron: fetch fresh after input (chosen), fetch fresh for every screenshot, or
document the lag only. What landed:

- `Session::freshen(area)`: when input has gone out since the whole frame was last refreshed,
  request `area` non-incrementally and wait for an update that covers it. A full-frame refresh
  marks the cache fresh until the next input, so idle screenshots stay free.
- `wait_for_change`: after our input, each apparent settle is checked against a refresh of the
  area; a difference counts as a change and the settle starts over.
- Refreshes ride the input queue, so the request reaches the server after the input it follows.
  An update already in flight that happens to cover the area also completes a refresh; telling
  the two apart would need the Fence extension, which Apple's server is not known to offer.
- `tests/support/stalling.rs` mocks the stall: a click paints a menu, incremental updates carry
  only highlight bands, and only non-incremental requests bring the menu. Both new e2e tests
  fail on the code before T-010.

## T-011 -- 2026-10-25

The live uat-007 run on macOS Screen Sharing found `scroll` correct but tiny. In the Applications
folder (icon view), with each wheel click a press and release of RFB button 4 or 5:

- `dy` 5 down moved the grid about 5 screen px, `dy` 5 up moved it back, and `dy` 20 moved it
  about 20: about one point per click, in the right direction, under the pointer.
- Five separate one-notch calls also moved it about 5 px, so spacing the clicks changes nothing.
- RFB's wheel is a fixed click with no amount. Apple's own viewer sends an unpublished
  high-resolution wheel message instead, and other VNC viewers report the same slow scrolling into
  Macs (Devolutions and Jump Desktop forums).

Options put to Aaron: scale clicks on Apple's server (chosen), document it and raise the 100-notch
cap, reverse-engineer Apple's wheel message, or leave it. What landed: the handshake records
Apple's `003.889` greeting on `Desktop`, and `scroll` sends `APPLE_WHEEL_CLICKS` (16, a line of
13-point macOS text) per notch there. `tests/support/stalling.rs` now greets as Apple and reports
pointer events; its new e2e test fails with one click per notch.

## T-012 -- 2026-10-25

The host running the agents was downloading about 27 MB/s with nobody at the Mac. All of it came
from three peephole copies, one per Claude Code session that had started it, since it was
registered in user scope. The copy in this session alone received 63.5 MB in 5 s (12.7 MB/s,
from `ss` byte counters) while no tool was called. The Mac was showing its screensaver, a
full-screen video. The writer re-armed an incremental request after every update, at most every
100 ms, whether or not any tool was in use. So an idle session pulled about 1.3 MB of video ten
times a second for as long as it ran.

Aaron's call: pause, connect lazily, and disconnect. What landed:

- `Idle { pause: 30 s, disconnect: 10 min }` in `SessionConfig`. The task dials only once a tool
  calls `Session::ready` (`screen_info` included), so a session that never uses peephole never
  touches the server.
- After `pause` without a tool, the writer stops re-arming update requests and marks the cache
  paused. The next `ready` fetches the whole frame non-incrementally before returning, and that
  update restarts the stream. Even input tools wait for it: otherwise a `wait_for_change` after a
  click would take its baseline after the click.
- `wait_for_change` holds the stream open for its whole wait, which can outlast `pause`.
- After `disconnect` without a tool, the connection closes and the state reads `idle`; the next
  tool reconnects. The state flips before the socket closes, so no tool mistakes the closing
  connection for a live one. That window is a few instructions wide, and no test pins it.
- Refreshes now have a queue in view-only sessions too. `Input`, which only a non-view-only
  session has, is still the only way to send a key or pointer event.
- `tests/session.rs` checks each mechanism against `tests/support/video.rs`. Each test fails with
  the mechanism it covers disabled: no pause, no busy guard, an eager connect, no idle disconnect.

The MCP registration moved from user scope to local scope in the two directories whose sessions
drive the Mac (machine config, not in the repo).
